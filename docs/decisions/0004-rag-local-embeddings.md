# 0004 — RAG: локальні ембеддинги й гібридний пошук у DuckDB

**Контекст.** Агенту потрібен пошук по текстах досліджень (FLEX зараз, ~10 досліджень далі). БД — один read-only файл DuckDB ([0001](0001-duckdb-single-file.md)), який перезбирається на проді bootstrap-ом при зміні коду. Ембеддинги треба рахувати однією моделлю і на збірці, і для кожного запиту.

**Рішення.**
- Модель — локальна `BAAI/bge-small-en-v1.5` через `fastembed` (ONNX), запечена в Docker-образ. Не API-провайдер.
- Вектори й FTS-індекс — у таблиці `chunks` того ж `flame.duckdb`; пошук — повний перебір `array_cosine_similarity` + BM25 (`fts`), злиття RRF. Без `vss`/HNSW.
- Ембеддинги кешуються між збірками за хешем тексту чанка.

**Наслідки.**
- (+) Без секретів і мережевих викликів; детерміновано; безкоштовно; CI тестує з фейковим embedder.
- (+) Нічого не змінюється в інфраструктурі Railway.
- (−) Образ більший на ~130 МБ моделі + onnxruntime; процес API з моделлю ~380 МБ RSS.
- (−) Якість трохи нижча за великі API-моделі; англомовна модель — запити агент формулює англійською.
- Переглянути, якщо recall@5 < 0.8 після тюнингу чанкінгу, або корпус > ~500 тис. чанків.
