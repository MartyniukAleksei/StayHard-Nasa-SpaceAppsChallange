# 0007 — Деплой на Railway запускає GitHub Actions, а не лише автодеплой Railway

**Контекст.** 2026-11-15 мердж PR #10 (автор коміту — учасник команди, не учасник Railway-воркспейсу) задеплоїв бекенд, а фронтенд завис у `WAITING` з `approvalReason: EXTERNAL_CONTRIBUTOR`. У дашборді це схоже на «чекає CI», хоча CI був зелений. Railway вимагає ручного *Approve* для комітів від GitHub-акаунтів, не прив'язаних до учасників воркспейсу; вимкнути цю перевірку не можна, а запросити учасників можна лише на плані Pro. Пише в `main` вся команда, тож кожен такий мердж чекав би на власника.

**Рішення.**
1. Job `deploy` у `.github/workflows/ci.yml` запускається на push у `main` після `backend`, `frontend`, `docker` і викликає `.github/scripts/railway_deploy.py` з секретом `RAILWAY_TOKEN` (project token, `production`).
2. Скрипт деплоїть лише сервіси, чия тека (`backend/`, `frontend/`) змінилася від коміту останнього успішного деплою (так само, як watch patterns, але й підхоплює пропущені деплої). Якщо автодеплой Railway цього коміту стартував — job за ним стежить; якщо ні (`WAITING`/немає) — `railway redeploy --from-source`. Job чекає `SUCCESS`, тож падіння деплою видно в CI.
3. Автодеплой Railway не вимикаємо: налаштування сервісів (root directory, Dockerfile, змінні, Volume) лишаються в Railway, `--from-source` бере той самий репозиторій і гілку.
4. CI на `main` більше не скасовується новим push-ем; деплої йдуть послідовно (`concurrency: deploy-production`).

**Наслідки.**
- (+) Деплой не залежить від автора коміту і не потребує ручних дій у Railway.
- (+) Статус деплою видно в GitHub (червоний `deploy`).
- (−) Ще один секрет (`RAILWAY_TOKEN`), який створює й ротує власник інфраструктури.
- (−) Коміт від не-учасника лишає в Railway старий `WAITING`-деплой, доки його не замінить новий (Railway позначає його `REMOVED`).
- Якщо перейдемо на Pro і запросимо всю команду, job просто стежитиме за автодеплоєм; скрипт можна лишити.
