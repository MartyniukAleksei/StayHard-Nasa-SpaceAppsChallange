# 0005 — Кадри камер з PSI на вимогу через Range-проксі

**Статус:** прийнято, 2026-11-15

## Контекст
Готове mp4 з борту є лише у 14 тестів FLEX із 274. Кадри камер (HiBMS, LLL-UV, кольорова) є у 253 тестів, але це zip-архіви по 16 МБ – 2.4 ГБ, ≈900 ГБ разом. Скопіювати їх на Volume нереально, а браузер не може ні ходити в PSI (CORS, протухлі лінки), ні показати 16-біт TIFF.

## Рішення
Бекенд (`flame.media`) читає кадри з PSI поштучно. S3, куди веде підписане посилання PSI, підтримує HTTP Range, тому з архіву читається лише центральний каталог zip, вкладений індекс кадрів і один запис кадру. Кадр конвертується в 8-біт JPEG із **фіксованим вікном яскравості на камеру** (A: весь 16-біт діапазон, B: 0–4095, бо UV-камера тьмяна), а не автоконтрастом, щоб послідовність не мерехтіла. Кеш (каталоги, індекси, ~128 кадрів, підписані лінки) живе в пам'яті процесу. Відповіді мають `Cache-Control: immutable`, решту кешує браузер.

Нові змінні, сервіси й записи в БД не потрібні: імена архівів беруться з `test_files`.

## Альтернативи
- **Офлайн витягти кілька кадрів на тест** у `build_db` або в новий реліз знімка. Дає швидкі прев'ю без PSI на рантаймі, але це новий сирий снапшот (рішення власника даних) і години завантажень. Можна додати пізніше поверх цього API.
- **Дисковий кеш на Volume.** Відкладено: Volume змонтовано для даних, а API в БД/знімок не пише. Якщо PSI буде повільним на демо, додамо окрему теку кешу.

## Наслідки
- Холодний кадр — 1–2 с, перший індекс архіву — 3–6 с. Для плеєра треба префетчити кадри наперед або брати рідші кадри (`max_side` зменшує розмір).
- Залежність від доступності PSI на рантаймі: при збої API повертає 502, і UI має показати це чесно.
- `t_ms` рахується від першого кадру; прив'язку до часу від запалювання (`t_s` у `ts_*`) ще треба зробити, це наступний крок для візуалізації.
- Кадр — це відображення, а не вимірювання. Числа в UI беруться з `ts_*`.
