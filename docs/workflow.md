# Командна робота (люди й агенти)

## Git
1. Нова задача → нова гілка від свіжого `main`: `git switch main && git pull && git switch -c <type>/<short-name>` (`feat/`, `fix/`, `docs/`, `data/`).
2. Маленькі коміти. У `main` можна і через PR, і прямим `git push` (після `git pull --rebase`). Перед пушем прогнати ті самі перевірки, що й CI.
3. На `main` заборонені лише force-push і видалення гілки. CI (`backend`, `frontend`, `docker (*)`) біжить після кожного пушу; на прод потрапляє лише коміт із зеленим CI, тож червоний CI на `main` — лагодимо одразу.
4. Після мерджу CI на `main` сам деплоїть змінений сервіс (job `deploy`, незалежно від того, хто автор коміту). Руками на Railway нічого не міняємо; якщо `deploy` червоний — пишемо власнику інфраструктури.

Один PR = одна задача в межах свого модуля (`flame/studies/flex`, `flame/rag`, `flame/agent`, `frontend/src/features/*`). Зміни спільного (`core/config.py`, `api/router.py`, `shared/`, схема БД у `build_db`) — окремим маленьким PR, щоб не конфліктувати.

## Дані й БД
| Що хочеш зробити | Як |
|---|---|
| Прочитати дані в API | SQL у `repository.py` свого модуля, лише читання з `flame.duckdb` |
| Нова таблиця / колонка / очищення / RAG-чанки / ембеддинги | Код у `flame/ingest/build_db.py` (або модуль у `BUILD_SOURCES`) → PR. Прод перезбере БД сам після мерджу |
| Нові сирі дані з PSI | Лише відповідальний за дані: змінює `psi_flex.py`, публікує реліз `data-flex-vN`, міняє `DATA_ARCHIVE_URL` у Railway, повідомляє команду |
| Отримати дані локально | [development.md → Дані](development.md) |

Заборонено: редагувати `data/flex` чи `flame.duckdb` руками, писати в БД з API, рахувати ембеддинги/звертатись до LLM під час `build_db` без кешу (див. ADR, коли з'явиться), змінювати чи видаляти опубліковані релізи даних.

## Секрети
Ключі (LLM тощо) — лише змінні сервісу в Railway і локальний `.env` (у git не потрапляє). У `.env.example` додаємо назву змінної без значення.
